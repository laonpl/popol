작업 단위로 쪼갠 것. **결론부터: 지적 대부분이 정당하다.** 특히 아래 세 개는 반박할 근거가 없다.

## 1. 완료 (2026-07-30)

### 1-1. 역량 · 증거 매핑 산출물 — 허점 4

리뷰 표현대로 "데이터는 이미 다 있고 조립만 없던" 것.

- 신규 [`frontend/src/utils/jdEvidenceMap.js`](../frontend/src/utils/jdEvidenceMap.js)
  - `collectRequirements(jobAnalysis)` — `requirements.essential` / `positionAnalysis.keyCompetencies` / `requirements.preferred` / `skillImportance` / `skills`를 한 목록으로 합치고 중복 제거, 필수→핵심역량→우대→스킬 순 정렬 (최대 18개)
  - `collectClaims(experiences)` — 근거 장부(`evidenceLedger.proofLevel` A~D) → 증거 번들(`status` 확보됨=B / 확인 필요=C / 추가 필요=D) → 경험 서술(D) → 직군 항목(D) 순으로 주장 수집
  - `buildJdEvidenceMap()` — 토큰 겹침 매칭. **AI 호출 없음 = 크레딧 0, 결과 재현 가능**
  - 매칭 임계값: 요구 역량 토큰의 50% 이상 등장 **또는** 서로 다른 토큰 2개 이상 등장. 애매하면 `matched`가 아니라 `gap`으로 남긴다 (억지 매칭 금지)
  - 상태 3종: `근거 있음`(A·B) / `서술만 있음`(C·D) / `공백`
- [`coreExperienceSections.js`](../frontend/src/utils/coreExperienceSections.js)에 `buildJdEvidenceSection` 추가
  - `buildCoreExperienceSections({ ..., jobAnalysis, expTitle })` 인자 추가, `buildCoreSectionsForExperience`가 `exp.jobAnalysis`를 자동 전달
  - **전 직군 공통 섹션**으로 꼬리에 배치 → 내보내기·노션·웹·PPT가 같은 목록을 공유하므로 한 번 추가로 모든 산출물에 반영
  - 기업 분석이 없으면 `enabled: false`로 빠진다

**근거 등급 노출 문제(허점 1)에 대한 결정**: 리뷰가 "전략적 선택이 미결"이라 지적한 지점.
리뷰가 제시한 절충안을 그대로 채택했다 — **산출물에는 A~D 등급을 싣지 않고**, 근거가 붙은 역량을
`[근거로 확인되는 역량]` 블록으로 앞에 세우고, 나머지는 등급 없이 `자료 보강이 필요한 역량` /
`보완 필요`로만 표기한다. 등급은 본인용 화면(면접 준비)에서만 보인다.

### 1-2. 면접 준비 산출물 — 허점 7

- 신규 [`frontend/src/utils/interviewPrep.js`](../frontend/src/utils/interviewPrep.js)
  - **예상 질문 ↔ 내 근거**: 고정 질문지가 아니라 그 경험에 실제로 있는 필드에서 생성 (대안·결정 기준·본인 실행 범위·수치 측정 방법·막힌 지점·바뀐 판단·남은 한계). 각 질문에 사용자 본인 문장을 `basis`로 붙이고, 비면 `ready: false`로 그대로 노출
  - **파고들면 무너지는 지점**: ① 수치는 있는데 `outcomeEvidence` 없음 ② 결론만 있고 검토 대안 없음 ③ 본인 실행 범위 공백 ④ 증거 상태가 `추가 필요`/`확인 필요` ⑤ 근거 장부 C·D등급 — 각각에 교정 방법(`fix`) 동봉
  - **30초 / 2분 구두 버전**: `identitySignal.sentence` + 대표 성과 / CARL 4문장 압축
  - AI 호출 없음. 저장된 문장만 재배치한다
- 신규 [`frontend/src/components/InterviewPrepPanel.jsx`](../frontend/src/components/InterviewPrepPanel.jsx) — 3탭 + 문항별 복사
- [`ExperienceResult.jsx`](../frontend/src/pages/experience/ExperienceResult.jsx) 헤더에 `면접 준비` 버튼 (`채우면 좋은 항목` 옆)

**중요 — 노출 경계**: 취약 지점은 **지원자 본인용**이다. 채용담당자에게 나가는
`coreExperienceSections`에는 넣지 않았다. 리뷰는 이 산출물을 "사용자가 미리 알아야 하는 정보"로
규정했고, 그 규정대로 경계를 코드 주석·패널 헤더 양쪽에 명시했다.

## 2. 다음 (원래 계획 — 위 1-B에서 대부분 소화됨)

### P1 — 자기기재 수치와 AI 추출 수치를 구분한다 (허점 2, 무결성)

리뷰의 가장 날카로운 지적. 프롬프트는 "근거 없으면 비워라"라고 강제하는데, 사용자가 그 빈칸을
기억으로 채우면 **D급 숫자가 A급 시각화(게이지·퍼널)로 렌더된다.** 안티-과장 장치가 시각화 욕구로 우회된다.

- `portfolioVisuals` 항목에 `source: 'ai' | 'self'` 필드 추가
- [`VisualDataEditor.jsx`](../frontend/src/components/portfolio/VisualDataEditor.jsx)에서 사용자가 값을 넣거나 고치면 자동으로 `source: 'self'`
- [`JobVisuals.jsx`](../frontend/src/components/portfolio/JobVisuals.jsx) 프리미티브 7종에서 `self`는 점선 테두리 + "본인 기재" 캡션
- [`missingFields.js`](../frontend/src/utils/missingFields.js)로 채운 값도 동일 처리
- 검증: 같은 경험을 AI 추출 / 수동 입력 두 경로로 만들어 산출물에서 구분되는지 눈으로 확인

### P1 — ATS 파싱 테스트 (허점 3)

"합격자형 프리미엄(추천)"이 파싱 실패 템플릿이면 추천 자체가 사용자에게 피해다. 확인한 기록이 없다.

- 노션형 11종 + 웹 4종을 PDF로 내보내 파서에 투입, 이름·경력 기간·스킬·직무명 생존 확인
- 실패 템플릿에는 "ATS 제출용 아님" 라벨 또는 추천 해제
- 3단 레이아웃·다크 배경·마퀴가 특히 의심 대상
- 결과를 [경험정리_산출물_체계.md](경험정리_산출물_체계.md) 6-1/6-2 표에 열로 추가

### P1 — 이력서 산출물 강화 (허점 3)

퍼널 첫 관문에 가치가 가장 적게 들어간 산출물이 놓여 있다. 현재 "인적사항·학력·경력·기술만 추린" 정의는
시스템의 차별점(판단·근거)을 정확히 걷어낸 버전이다.

- `decisionTrace.choice` + `outcomeEvidence`에서 성과 bullet 생성 (marketer의 `resumeBullets` 공식을 전 직군으로)
- `jobAnalysis`가 있으면 요구 역량 순서에 맞춰 bullet 재정렬 (§1-1 매핑 재사용)
- 1분 읽기용 한 장 요약 산출물(요구 역량 상위 5개 × 근거 1줄) 신설 — 현재 60초 판단용 산출물이 아예 없음

### P2 — 맥락·권한·규모 필드 (허점 5)

스타트업 PM과 대기업 PM이 같은 렌즈로 읽히는 문제. `decisionTrace.situation`에 녹아 있어 비교가 불가능하다.

- `keyExperiences[]`에 구조화 필드 4개 추가: `teamSize` / `myAuthority`(권한 범위) / `scale`(트래픽·예산·사용자 규모) / `constraints`
- `careerFieldProfiles`의 각 `schema`가 아니라 **공통 스키마**에 넣는다 (직군 무관 비교 축이므로)
- 산출물에서는 경험 카드 상단 메타 줄로 노출

### P2 — 경력 단계 세분화 (허점 5)

원티드랩 조사에서 4~7년차 수요가 49.7%인데 `experienced` 하나가 3년차와 12년차를 같이 담는다.
문체만의 문제가 아니라 **8년+ 성과는 "타인을 통해 낸 것"인데 현재 스키마의 모든 필드가 1인칭 판단 기록**이다.

- `CAREER_STAGES`를 4~5단계로 분할 (`first` / `newgrad` / `mid`(3~7년) / `senior`(8년+))
- `senior`용 레버리지형 추출 단위 신설: 위임·채용·프로세스 설계·후배 판단 교정
- ⚠️ [`careerStages.js`](../frontend/src/constants/careerStages.js) ↔ [`buildHumanVoiceRules`](../backend/src/prompts/experiencePrompts.js#L163) 동시 수정 필수
- 기존 데이터 마이그레이션 필요 (`experienced` → `mid` 기본값)

### P2 — 빈칸 서열화 (사용자 이탈)

정직한 AI일수록 빈칸이 많고, 지금은 20개 빈칸이 전부 동등한 무게로 제시된다. 품질 설계의 정당한
결과지만 이탈의 직접 원인. **정직성의 비용이 전부 사용자에게 전가돼 있다.**

- `missingFields`에 `impact: 'critical' | 'nice'` 등급 부여 — "이 3개를 채우면 서류 통과 판단이 달라진다"
- critical 기준: 본인 실행 범위 / 결과 확인 근거 / 필수 요구역량 공백(§1-1 매핑 연동)
- 20개 나열이 아니라 질문 1개씩 유도 — 인터뷰 파이프라인 재사용

### P2 — voiceRecord 사용 지점 명시 (허점 6)

`originalQuote` / `polished` / `aiMeaning` 중 산출물이 무엇을 쓰는지 코드에 명시가 없다.
`polished`를 쓰면 원문 보존 설계가 마지막 한 걸음에서 무의미해진다.

- 회고·판단 섹션은 `originalQuote`를 인용 표시(`" "`)로 그대로 노출
- 분석 문체가 필요한 곳만 `aiMeaning`
- 산출물별 사용 필드를 체계 문서에 표로 고정

### P3 — 직군 정의 단일 소스화 (유지보수 부채)

직군 하나 추가에 5곳 수정. 이미 부채 증거가 쌓였다(`visual-10~12` 미노출, `web-2/5` 랩 전용,
"전 직군이 common으로 보이던" 버그). 방치하면 24직군 특화가 24개 라벨로 퇴화한다.

- 직군 정의를 백엔드 `CAREER_FIELD_PROFILES` 단일 소스로 두고 프론트는 API로 파생
- 또는 최소한 공유 JSON 하나에서 양쪽이 읽게 한다

### P3 — 지표 수집 (가장 큰 허점)

체계 문서에 성과 지표가 한 줄도 없다. **피드백 루프가 없으면 "인사담당자가 원하는 방식인가"는 영원히 추정이다.**

- 서류 통과율 / 면접 진행율 (사용자 자기보고, 경험별 태깅)
- 공개 링크(`/p/:id`) 체류·스크롤 뎁스 — 어느 섹션이 실제로 읽혔는지
- **AI 출력 수정률** — 사용자가 얼마나 고쳐 썼는지 = 품질 프록시. 지금도 계산 가능(원본 vs 저장본 diff)
- 템플릿별 결과 분포
- `@vercel/analytics`가 이미 들어 있으므로 이벤트만 얹으면 된다

## 3. 코드로 안 되는 검증 3건

리뷰가 제안한 실험. 개발이 아니라 **사람을 붙여야** 하는 일이다.

| 실험 | 방법 | 이 실험이 답하는 질문 |
|---|---|---|
| 블라인드 리뷰 | 같은 원본으로 (a) 우리 산출물 (b) 일반 AI 도구 산출물 (c) 잘 쓴 수동 포트폴리오를 만들어 인사담당자 15~20명에게 순서 무작위 제시. 서류 통과 여부 + 물어볼 질문 3개 + "AI로 쓴 것 같은 것" 지목 | 허점 6 (AI 문체 지문). 마지막 항목이 즉답을 준다 |
| ATS 파싱 테스트 | 15개 템플릿 PDF를 실제 파서에 투입 | 허점 3. 실패 템플릿이 "추천"이면 즉시 사용자 피해 |
| 근거 등급 노출 실험 | 등급 노출 / 미노출 두 버전을 같은 심사자에게 | **시스템 전체 철학의 시장 가치**가 이 실험에 걸려 있다 |

세 번째가 특히 중요하다. §1-1에서 "등급 숨김 + 근거 있는 것 앞세우기"로 결정했지만,
그건 실험 없이 내린 잠정 결정이다. 결과에 따라 되돌릴 수 있게 섹션 빌더 한 곳에만 로직을 뒀다.

## 4. 리뷰가 못 본 것 — 우리 쪽 사실 정정

리뷰는 문서만 보고 판단했으므로 아래는 실제 코드와 다르다. 반영에서 제외한다.

- **"외부 검증 경로가 GitInsights 하나뿐"** — 대체로 맞지만 `importService`가 Notion·GitHub·블로그 URL을
  실제로 가져와 파싱하고, `researchMarketMetrics`가 검색 기반으로 시장 수치를 확인하며,
  `groundAnalysisMetrics`/`groundMomentMetrics`가 AI가 만든 수치를 **원문에 없으면 제거**한다.
  즉 "자기신고"보다는 한 단계 위다. 다만 **링크 생존 확인·날짜 검증·제3자 확인이 없다**는 핵심 지적은 유효하다.
- **"jobAnalysis가 산출물에 없다"** — 정확했다. 게다가 `StructuredResult`의 기업 분석 사이드바는
  `className="... hidden"`으로 **UI 자체가 숨겨져 있었다.** 지적보다 상태가 더 나빴다.

## 5. 반영하지 않거나 형태를 바꾼 것

| 리뷰 제안 | 판단 |
|---|---|
| 근거 등급(A~D)을 심사자에게 노출 | **미채택.** 리뷰 자신이 "노출하면 D급이 감점"이라고 양면을 인정했다. 리뷰가 제시한 절충안(근거 있는 것만 앞 블록)만 채택하고, 등급 노출은 §3 실험 결과를 보고 결정 |
| 스킬 기반 매칭으로 단위를 전환 | **부분 채택.** 경험 단위를 버리지 않는다. 경험 정리는 판단 과정을 보존하는 데 필요하고, 역량↔증거는 그 위에 얹는 **뷰**로 구현했다(§1-1). 단위 자체를 바꾸면 24직군 렌즈 전체가 무의미해진다 |
| JD 키워드 매핑을 전 직군 필수 출력으로 | **채택했으나 형태 변경.** 직군 섹션이 아니라 산출물 꼬리의 공통 섹션으로 넣었다. 직군 섹션에 넣으면 24곳을 고쳐야 하고 §3-1의 부채를 키운다 |
| 면접 준비를 서류 산출물에 포함 | **명시적 거부.** 취약 지점을 채용담당자에게 보내면 안 된다. 본인용 패널로만 구현 |

## 6. 작업 순서 제안

```
1) P1 자기기재 수치 마킹      — 무결성. 지금 안 하면 계속 잘못된 숫자가 나감
2) P1 ATS 파싱 테스트          — 사용자 피해 가능성. 하루면 확인됨
3) P3 지표 수집(최소 3개)      — 이게 없으면 아래 전부 추정으로 남는다
4) P1 이력서 강화 + 한 장 요약  — 퍼널 첫 관문
5) P2 빈칸 서열화              — 이탈 방어
6) P2 맥락·규모 필드 → 경력 단계 분할 (스키마 변경이므로 묶어서)
7) P3 직군 정의 단일 소스화
```

3번을 4번보다 앞에 둔 이유: 지표가 없으면 4~7번의 효과를 영원히 알 수 없다.

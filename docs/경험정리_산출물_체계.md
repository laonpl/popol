# 경험 정리 방식 · 산출물 체계 (2026-07 기준)

지금까지 만들어 놓은 것을 **분야별 경험 정리 방식**과 **산출물**로 나눠 정리한 지도.
목적은 "무엇이 어디에 구현돼 있고, 하나를 바꾸면 무엇이 같이 바뀌어야 하는가"를 한 화면에서 보는 것.

- 이 문서는 요약이 아니라 **코드 포인터**다. 값이 궁금하면 링크된 파일이 항상 진실이다.
- 표에 적힌 라벨·단위·스키마는 모두 실제 코드에서 옮겼다. 코드를 고치면 이 문서도 같이 고쳐야 한다.
- 마지막 절 [9. 동기화 규칙](#9-동기화-규칙--한-곳을-바꾸면-같이-바꿔야-하는-곳)에 "짝지어 움직이는 파일" 목록이 있다.

## 1. 전체 파이프라인

```
[입력]  직접 작성 / 인터뷰 / 채팅 / 파일 업로드(PDF·HWP·PPT·DOCX) / URL(Notion·GitHub·블로그)
   ↓
[분석]  POST /api/experience/analyze  →  analyzeExperience()
        3단계 병렬 호출: Overview(7섹션+직군섹션) ‖ KeyExp×N ‖ Meta
   ↓
[경험 데이터]  structuredResult
        7섹션 + jobSpecific + keyExperiences[] (jobData·decisionTrace·voiceRecord·
        evidenceBundle·identitySignal·honestReview) + artifactAnalysis + portfolioVisuals
   ↓
[구성 계획]  POST /api/job/compose-experience  →  경험별 서사 골격·섹션 순서·히어로 선택
   ↓
[산출물]  노션형 문서 · 웹사이트 · PPT · PDF · 이력서 · 공유 링크
```

| 단계 | 코드 |
|---|---|
| 분석 진입 | [`backend/src/routes/experience.js:84`](../backend/src/routes/experience.js#L84) |
| 3단계 병렬 분석 | [`geminiService.js:1348` analyzeExperience](../backend/src/services/geminiService.js#L1348) |
| 실패 시 폴백 | [`geminiService.js:1088` buildFallbackExperienceAnalysis](../backend/src/services/geminiService.js#L1088) |
| 수치 근거 검증(그라운딩) | [`geminiService.js:2218` groundAnalysisMetrics](../backend/src/services/geminiService.js#L2218) |
| 구성 계획 프롬프트 | [`portfolioPrompts.js:810` buildExperienceCompositionPrompt](../backend/src/prompts/portfolioPrompts.js#L810) |

원문 입력 한도: 섹션당 6,000자, 전체 18,000자로 자른다 ([`geminiService.js:1356`](../backend/src/services/geminiService.js#L1356)).

## 2. 정리 기준이 달라지는 3개 축

같은 경험도 아래 세 축에 따라 **추출 단위·문체·섹션 구성**이 달라진다.

| 축 | 값 | 정의 위치 |
|---|---|---|
| 직군 (24) | common + 23개 대분야 | [`careerFieldProfiles.js:15`](../backend/src/prompts/careerFieldProfiles.js#L15) |
| 경력 단계 (4) | `first` 첫 취업 / `newgrad` 신입 / `experienced` 경력 이직 3~7년 / `lead` 리드 8년+ | [`careerStages.js`](../frontend/src/constants/careerStages.js) ↔ 백엔드 [`CAREER_STAGE_RULES`](../backend/src/prompts/experiencePrompts.js#L163) |
| 기업 분석 유무 | 채용공고 분석 결과(`jobAnalysis`) 있으면 그 기준으로 재구성 | [`jobAnalysisService.js`](../backend/src/services/jobAnalysisService.js) |

경력 단계는 문체 규칙을 바꾼다 — 첫 취업자에게 실무 성과 문법을 강요하면 거짓말처럼 읽히고, 경력자에게 학생 톤을 쓰면 미숙해 보인다는 판단이 코드 주석에 남아 있다.

## 3. 분야별 경험 정리 방식

### 3-1. 직군 라우팅

세부 직무는 끝없이 늘어나므로, **채용 평가 방식이 유사한 23개 대분야 + common**으로 alias 라우팅한다.
등록되지 않은 직무는 `common` 렌즈로도 증거 중심 추출이 된다.

- 라우팅: [`normalizeCareerField` / `getCareerFieldProfile`](../backend/src/prompts/careerFieldProfiles.js#L368)

### 3-2. 분야별 렌즈 — 6요소

| 요소 | 뜻 |
|---|---|
| `unit` | 경험을 세는 단위 (무엇을 1건으로 보는가) |
| `emphasis` | 무엇을 보여주고 무엇을 덜 보여줄지 |
| `artifacts` | 이 직군에서 증거가 되는 산출물 종류 |
| `proofSignals` | 강한 증거로 인정하는 신호 |
| `metrics` | 확인할 지표 |
| `cautions` | 과대 해석을 막는 금지 규칙 |
| `schema` | 이 직군 전용 `jobData` JSON 스키마 |
| `sections` | 직군 전용 서술 섹션 (있는 직군만) |

### 3-4. 산출물 판독 → 근거 장부 (모든 직군 공통 전처리)

입력은 완성된 포트폴리오가 아니라 코드·화면·기획서·초안·회의록이 섞인 묶음이라는 전제로,
문장을 쓰기 전에 4단계를 강제한다 ([`buildArtifactIntelligenceGuide`](../backend/src/prompts/careerFieldProfiles.js#L417)).

1. **자료 경계 보존** — 파일·링크·화면·버전마다 `ART-001`부터 id 부여. 확장자 대신 내용으로 `kind`/`stage`(계획·실행·검증·결과·회고·복합) 판별.
2. **사실 상태 분리** — 제안했다 ≠ 승인됐다 ≠ 실행했다 ≠ 효과가 검증됐다. 화면/프로토타입은 설계 증거이지 출시 효과의 증거가 아니다.
3. **근거 강도 A~D** — A 시스템 로그·발행물·원데이터 / B 본인 초안·승인·회의록 / C 출처 불완전한 캡처 / D 회상만 있는 주장.
4. **직군 렌즈 적용** — 위 3-2의 6요소로 같은 자료를 다시 읽되, 자료에 없는 직무 활동을 만들어 번역하지 않는다.

결과는 `artifactAnalysis`(detectedArtifacts / evidenceLedger / experienceCandidates / conflicts)로 저장되고,
이후 모든 경험 카드가 `artifactRefs`로 이 장부를 참조한다. 스키마: [`ARTIFACT_ANALYSIS_SCHEMA`](../backend/src/prompts/careerFieldProfiles.js#L377).

### 3-5. 경험 카드 공통 스키마 (직군 무관)

성과 문장(CARL)보다 **판단 과정·말투·증거**를 보존하는 것이 핵심 산출물이다.
정의: [`experiencePrompts.js:205` HONEST_REVIEW_SCHEMA / DECISION_RECORD_SCHEMA](../backend/src/prompts/experiencePrompts.js#L205)

| 묶음 | 필드 | 역할 |
|---|---|---|
| CARL 4문장 | `context` `action` `result` `learning` | 읽기용 요약 |
| `decisionTrace` | situation → problemJudgment → problemEvidence → alternatives[] → decisionCriteria[] → choice → execution → outcomeEvidence → changedJudgment → newPrinciple | 판단 지도. 실제로 검토한 대안만 기록 |
| `voiceRecord` | originalQuote / polished / aiMeaning | 사용자의 실제 말투 보존 (조사·어미 임의 수정 금지) |
| `evidenceBundle[]` | claim / type / sourceRef / whatItProves / ownership / status | 증거 번들 |
| `identitySignal` | pattern / sentence / proof / confidence | 나를 보여주는 한 문장 |
| `honestReview` | struggle / misjudgment / limitation / nextTime | 솔직 회고 (막힌 지점·예상과 달랐던 점·남은 한계·다시 한다면) |
| `scope` | teamSize / myAuthority / scale / constraints | **경험의 이식성 축.** 같은 직무도 규모·권한이 다르면 다른 경험이다 |
| `jobData` | 직군별 스키마 (3-2의 `schema`) | 직군 특화 추출 |

### 4-3. 경험을 가로지르는 산출물 (경험이 쌓일수록 두꺼워짐)

[`careerNarrative.js`](../frontend/src/utils/careerNarrative.js) — 경험 1건은 취향이지만 반복되면 패턴이라는 전제.

- **나를 보여주는 한 문장**: `identitySignal.pattern` 빈도 → 3회 이상 `검증됨` / 2회 `관찰 중` / 1회 `가설`
- **판단 원칙**: `decisionTrace.newPrinciple` 누적
- 렌더: [`CareerNarrativeSections.jsx`](../frontend/src/components/CareerNarrativeSections.jsx)

### 4-3-b. 역량 · 증거 매핑 (기업 분석 있을 때)

[`jdEvidenceMap.js`](../frontend/src/utils/jdEvidenceMap.js) — 공고 요구 역량 × 그것을 증명하는 내 증거 × 공백.
`requirements.essential` / `keyCompetencies` / `preferred` / `skillImportance`를 심사 기준 목록으로 합치고,
근거 장부(A~D) → 증거 번들(확보됨/확인 필요/추가 필요) → 경험 서술 순으로 매칭한다. AI 호출 없음(토큰 겹침).

- 상태 3종: `근거 있음`(A·B) / `서술만 있음`(C·D) / `공백`
- **산출물에는 A~D 등급을 싣지 않는다** — 심사자에게 등급은 감점 신호로 읽힌다. 근거가 붙은 역량을 앞에 세우고 나머지는 "보완 필요"로만 표기 (잠정 결정, [피드백 반영 계획 §3](피드백_반영_계획.md) 실험 후 재검토)

### 4-3-c. 면접 준비 (본인용, 산출물 아님)

[`interviewPrep.js`](../frontend/src/utils/interviewPrep.js) + [`InterviewPrepPanel.jsx`](../frontend/src/components/InterviewPrepPanel.jsx)

`decisionTrace`·`honestReview`·`evidenceBundle`은 사실 면접 답변의 원재료다. 예상 질문 ↔ 내 근거,
파고들면 무너지는 지점(수치에 근거 미연결 / 대안 없음 / 본인 범위 공백 / 증거 미확보 / 근거 C·D급),
30초·2분 구두 버전을 만든다.

> ⚠️ **취약 지점은 채용담당자에게 나가는 산출물에 절대 포함하지 않는다.** `coreExperienceSections`에 넣지 않은 이유.

### 4-4. 빈칸 처리

AI는 원본에 근거가 없으면 값을 비운다. 본문에서는 `[작성 필요]` 류를 지우고,

그룹: `프로젝트 기본` / `본문 섹션` / `직군 항목` / `핵심 경험 N` / `솔직 회고 N`.

## 8. 직군 데이터가 화면까지 오는 경로

직군 특화가 중간에서 버려지면 6개 직군이 전부 같은 카드로 보인다 (실제로 있었던 버그).

```
jobCategory 선택 (JOB_CATEGORIES)

  → 프롬프트: buildArtifactIntelligenceGuide + buildFieldKeyExperienceAddon

  → 저장 (Firestore)

  → 산출물: buildCoreExperienceSections(jobCategory) → 내보내기·노션·웹·PPT
```

이 사슬 중 한 곳만 `jobCategory`를 흘리면 전 직군이 `common`으로 보인다. 디버깅은 항상 이 순서로.

- `visual-10` `visual-11` `visual-12` — 렌더러만 있고 노출 경로 없음 (6-1)
- PPT는 사용자 업로드 템플릿 의존이라 "우리 디자인"으로 보여줄 대표 산출물이 없음 (6-3)
- `web-2` `web-5` — 랩 전용으로 남아 있음 (6-2)
- **ATS 파싱 미검증** — 노션 11종·웹 4종이 이력서 파서를 통과하는지 확인한 기록이 없다. "합격자형 프리미엄(추천)"이 실패 템플릿일 수 있다 ([계획 P1](피드백_반영_계획.md))
- **근거의 외부 검증 부재** — 근거 강도 A~D를 지원자 신고에 의존한다. 링크 생존·날짜·제3자 확인이 없다
- **성과 지표 축적 전** — [`outcomeMetrics.js`](../frontend/src/services/outcomeMetrics.js)를 심었지만 데이터가 쌓이기 전까지 산출물 구성의 효과는 추정이다

## 11. 산출물 요약 (심사자용 / 본인용)

노출 경계를 섞으면 안 된다. 취약 지점을 채용담당자에게 보내는 것은 사고다.

| 산출물 | 대상 | 위치 |
|---|---|---|

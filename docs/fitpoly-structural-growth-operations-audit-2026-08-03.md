# 핏폴리 구조·성장·운영 종합 진단

작성일: 2026-08-03  
범위: 제품 구조, 실제 사용 데이터, 이탈 원인, AI·내보내기 파이프라인, 결제, 보안·개인정보, 경쟁 환경, KPI, 운영 체계, 12주 로드맵

> 이 문서는 2026-08-03 시점 코드와 Firebase 집계값을 읽기 전용으로 점검한 결과다. 사용자 식별 정보와 원문 이력서는 사용하지 않았다. 법률·회계 판단은 별도 전문가 검토가 필요하다.

## 1. 한 문장 결론

핏폴리가 가져가야 할 자리는 **“AI 포트폴리오 제작기”가 아니라, 흩어진 경력 증거를 검증 가능한 단위로 구조화하고 지원 회사마다 재사용하는 커리어 증거 운영체계**다.

현재는 입력·분석·편집·템플릿·PDF/PPT·공개 링크·결제까지 기능 폭은 넓지만, 핵심 가치가 전달됐는지 확인할 사건 데이터가 없고, 사용자가 `경험 구조화 → 증거 확인 → 지원처별 결과물 → 재사용`의 루프를 완주하도록 제품 구조가 강제하지 않는다. 그 결과 “문서를 하나 생성했다”는 수치는 많아도 실제 취업 지원에 쓸 수 있는 결과물과 재방문, 결제까지 이어지는지는 알 수 없다.

가장 중요한 일은 새 기능이나 템플릿 추가가 아니다. 앞으로 12주는 다음 순서가 맞다.

1. 정확한 퍼널과 결제 원장을 만든다.
2. 첫 자료 한 개를 넣어 검증된 경험 하나와 쓸 수 있는 결과물 하나를 얻는 기본 경로를 단순화한다.
3. PDF/PPT·결제·삭제·권한 같은 신뢰 경로의 실패를 먼저 없앤다.
4. 두 번째 지원 회사에서 같은 증거를 다시 쓰게 만들어 반복 사용을 검증한다.
5. 이 네 가지가 확인된 뒤에만 직무, 템플릿, 유입 채널을 확장한다.

## 2. 조사 방법과 판단 등급

### 조사한 것

- 프론트엔드 경로, 온보딩, 경험 분석, 포트폴리오 편집, 내보내기, 결제·관리자 화면
- 백엔드 인증, AI 라우팅, 파일·URL 가져오기, PDF/PPT 생성, 크레딧, 계정 삭제
- Firebase Authentication 및 주요 컬렉션의 익명 집계
- 빌드 결과, 번들 크기, 의존성 취약점, 오류 로그 분포
- 공식 경쟁 제품과 인접 대체재의 공개 기능
- Gemini, Render, 개인정보보호위원회 등의 공식 문서

### 판단 등급

- **확인**: 코드 또는 현재 집계에서 직접 확인
- **추정**: 구조와 수치가 강하게 시사하지만 사건 추적이 없어 인과관계를 아직 증명하지 못함
- **검증 필요**: 인터뷰나 실험으로 판정해야 하는 가설

현재 가장 큰 분석 한계는 제품 행동 이벤트가 없다는 점이다. Firebase 컬렉션의 생성 개수는 볼 수 있지만, 화면을 본 순서, 실패 후 이탈, 실제 지원에 사용했는지, D7/D30 복귀는 재구성할 수 없다.

## 3. 현재 서비스의 실제 구조

### 의도된 가치 사슬

```text
흩어진 자료
  파일 · GitHub · 블로그 · Notion · 직접 입력
        ↓
AI 경험 추출·구조화
  역할 · 행동 · 성과 · 역량 · 근거
        ↓
채용공고 연결
  요구 역량과 경험 매칭
        ↓
지원 결과물
  포트폴리오 · 웹 · Notion · PDF · PPT
        ↓
공유·지원·결과 회수
        ↓
다음 회사에 증거 재사용
```

### 이 구조로 가능한 것

1. **한 번 수집한 경험을 여러 결과물에 재사용**  
   포트폴리오 문구를 매번 새로 쓰는 대신, 경험을 원천 데이터로 두고 직무·회사·공고에 맞게 조합할 수 있다.

2. **자료 형식과 결과물 형식을 분리**  
   실제 사용에서도 가져오기 741건 중 파일이 650건이었고, GitHub 45건, 블로그 33건, Notion 13건이 있었다. “흩어진 자료를 한곳에 넣고 싶다”는 입력 수요는 확인된다.

3. **검증 가능한 경험 그래프 구축**  
   각 주장에 원문 위치, 사용자가 확인한 사실, 수치, 기여도, 직무 역량을 연결하면 일반 생성형 이력서 도구보다 강한 데이터 자산이 된다.

4. **지원 회사마다 낮은 추가 비용으로 변형**  
   같은 경험을 채용공고 요구사항에 맞춰 선택·정렬하되, 사실 자체는 바꾸지 않는 구조를 만들 수 있다.

5. **성과 데이터로 품질 개선**  
   사용자의 동의를 받고 지원·서류 통과·면접 결과를 연결하면 “어떤 근거가 어떤 공고에서 실제로 쓰이고 성과를 냈는지” 학습할 수 있다. 지금은 결과 수집 기능이 없어 잠재력 단계다.

### 현재 실제 경로

코드상 사용자는 경험 분석 없이도 포트폴리오를 만들 수 있다. 실제로도 포트폴리오 생성 사용자 157명 중 88명, 즉 56.1%가 경험 데이터 없이 포트폴리오부터 만들었다. 이는 사용자의 자유도를 높이지만, 핏폴리의 차별점인 “증거 기반 구조화”를 우회하게 만든다.

따라서 현재 제품은 하나가 아니라 두 제품처럼 작동한다.

- 경로 A: 자료 가져오기 → 경험 분석 → 결과물 생성
- 경로 B: 빈 포트폴리오/템플릿 → 직접 편집

경로 B는 Canva·Notion 같은 강한 대체재와 바로 경쟁하게 만들고, 경로 A가 제공할 수 있는 고유한 가치를 희석한다.

### 이 수치가 말해 주는 것

#### 1. 첫 세션이 거의 전부다 — 확인

- 첫 경험을 만든 98명 중 83명이 가입 24시간 안에 만들었다.
- 첫 포트폴리오를 만든 157명 중 139명이 24시간 안에 만들었다.
- 처음 자료를 가져온 96명 중 82명이 24시간 안에 가져왔다.

나중에 돌아와 처음 가치를 얻은 사용자는 매우 적다. 온보딩과 첫 실행에서 막힌 사용자를 이메일로 다시 데려오는 것보다, 첫 세션의 시간·선택·오류를 줄이는 편이 우선이다.

#### 2. “포트폴리오 생성”은 활성화가 아니다 — 확인

포트폴리오 사용자의 56.1%는 경험 데이터가 없다. 빈 문서나 템플릿을 만든 것만으로도 현재 집계에서는 성공처럼 보일 수 있다. 따라서 생성 수를 핵심 성과로 쓰면 제품 가치를 과대평가한다.

#### 3. 핵심 재사용 루프가 닫히지 않았다 — 확인

채용공고 매칭 문서는 2개다. 랜딩 페이지의 “지원 직무에 맞는 포트폴리오” 약속과 실제 제품 사용 사이에 큰 간격이 있다. 사용자가 공고를 붙여 넣지 않는 이유, 결과를 신뢰하지 않는 이유, 기능을 찾지 못하는 이유를 각각 측정해야 한다.

#### 4. 만족도 4.8은 제품시장적합성의 증거가 아니다 — 확인

피드백은 14건뿐이다. 응답자는 만족한 사용자로 치우칠 가능성이 크고, 비활성·이탈 사용자의 이유를 설명하지 못한다.

#### 5. “리텐션”은 아직 측정되지 않았다 — 확인

Firebase Auth의 최근 로그인 시각은 실제 제품 방문이나 가치 행동이 아니다. 현재 값으로는 최근 7일 로그인 9명, 30일 42명이라는 참고치만 볼 수 있다. 코호트별 D1/D7/D30 리텐션으로 부르면 안 된다.

### 기존 지표에서 바로 고쳐야 할 오류

- 컬렉션별 사용자 수를 독립적으로 세어 퍼널로 표시한다. 순서가 보장된 중첩 퍼널이 아니다.
- “활성화”가 포트폴리오 생성 또는 내보내기 사용자 합집합이라 빈 문서도 포함한다.
- 가치 도달 시간을 경험 문서 `createdAt`으로 계산해 AI 분석 완료까지 걸린 시간을 측정하지 않는다.
- “완성·내보내기”라는 이름의 지표가 실제로는 주간 포트폴리오 생성을 센다.
- 결제 주문에는 `userId`가 저장되는데 대시보드 일부는 `uid`로 결제 사용자를 읽어 유료 사용자를 누락한다.
- AI 사용 거래와 지갑 차감 총계가 일치하지 않아 비용·크레딧 원장의 완전성을 검증할 수 없다.

## 5. 사용자가 이탈할 가능성이 높은 지점

현재는 단계별 사건 데이터가 없으므로 아래는 **이탈 가설**이다. 각 항목에는 확인할 지표를 붙였다.

| 단계 | 이탈 원인 가설 | 현재 근거 | 반드시 기록할 사건 |
|---|---|---|---|
| 랜딩 → 가입 | 약속이 넓고 실제 결과 예시·전후 비교·출처가 약함. 민감한 경력 자료 업로드 신뢰가 부족함 | 랜딩의 강한 수치 주장과 간단한 개인정보 안내 | CTA 노출/클릭, 샘플 열람, 개인정보 안내 열람, 가입 시작/완료 |
| 가입 → 첫 자료 | 긴 프로필, 직무 선택, 여러 시작점 때문에 “무엇부터?”가 생김 | 프로필 완료 177, 건너뜀 116 | 온보딩 단계별 노출·완료·건너뜀·소요시간 |
| 자료 → 추출 | HWP/OCR/Notion 품질, 긴 대기, 파일 제한, 중간 복귀 불가 | 단일 프로세스, 메모리 업로드, 최근 API 오류 | 업로드 시작/완료, 파싱 결과, 큐 대기, 실패 코드, 재시도 |
| 추출 → 신뢰 | AI 문장이 일반적이거나 원문 근거가 보이지 않음. 없는 수치가 생길까 불안 | 모델 폴백과 휴리스틱 결과가 사용자에게 구분되지 않음 | 주장별 확인/수정/삭제, 원문 보기, 누락 질문 응답 |
| 신뢰 → 포트폴리오 | 템플릿 선택지가 많고 추천 이유가 없음. 경험 구조화를 건너뛸 수 있음 | Notion형이 68.5%, 경험 없는 포트폴리오 사용자 56.1% | 추천 노출, 선택 변경, 첫 콘텐츠 삽입, 빈 문서 이탈 |
| 편집 → 내보내기 | 편집기 무겁고 PDF/PPT 결과 차이·실패가 최종 신뢰를 훼손 | 약 11.2MB minified 코드 편집기 청크, 내보내기 오류 이력 | export_started/succeeded/failed, 포맷, 소요시간, 재시도 |
| 결과 → 재방문 | 포트폴리오 완성 뒤 돌아올 이유가 없음 | 채용공고 매칭 2건, 지원 결과 루프 없음 | 새 공고 연결, 두 번째 결과물, 지원 상태, 결과 입력 |
| 유료화 | 계좌이체와 승인 대기, 크레딧의 실제 결과 단위가 불명확 | 현재 UI는 수동 계좌이체 요청, 자동 주문과 데이터 분리 | checkout_started, request_submitted, approved, granted, refunded |

### 이탈을 제대로 알아내는 방법

정량 데이터만으로 “왜”는 알 수 없다. 다음 세 가지를 같은 주에 반복해야 한다.

1. **퍼널 사건**: 어느 단계에서 몇 명이 멈췄는지
2. **실패 맥락**: 오류 코드, 지연, 입력 형식, 디바이스, 재시도
3. **주 5명 인터뷰**: 막힌 사용자 3명 + 완주 사용자 2명

이탈 인터뷰에서는 “만족했나요?”보다 다음을 묻는다.

- 마지막으로 취업 자료를 만들던 실제 상황을 보여 달라.
- 핏폴리에 넣기 직전 자료는 어디에 있었나?
- 어느 화면에서 다음 행동을 확신하지 못했나?
- AI가 만든 문장 중 믿지 못하거나 고친 것은 무엇인가?
- 만든 결과물을 실제 어느 회사 지원에 썼나? 쓰지 않았다면 왜인가?
- 돈을 내는 대신 현재 어떤 도구와 수작업을 쓰나?

## 6. 파이프라인의 구조적 한계

### A. 제품 파이프라인

#### 경험이 결과물의 필수 원천이 아니다

핵심 자산은 경험 데이터여야 하지만 빈 포트폴리오 생성이 더 쉬운 경로로 존재한다. 이 구조에서는 템플릿 생성이 많아질수록 핵심 가치 검증이 오히려 어려워진다.

**개선:** 기본 경로를 `자료 1개 → 경험 근거 확인 → 추천 결과물 1개`로 고정한다. 빈 문서와 18개 템플릿은 “고급 설정”으로 내린다.

#### 너무 많은 직무와 출력 형식

23개 직무와 다양한 템플릿·출력 형식을 한 번에 유지하면 각 조합의 프롬프트, 편집, 반응형, PDF 품질을 충분히 검증하기 어렵다.

**개선:** 현재 프로필의 직무 필드가 사실상 비어 있어 승자 직무를 데이터로 고를 수 없다. 먼저 직무·지원기한·보유자료를 사건 속성으로 모으고, 4개 초기 직무의 골든 데이터셋으로 품질을 관리한다.

#### AI가 사실과 표현을 함께 결정

입력이 부족할 때 AI가 자연스러운 문장을 만들수록 사실성 위험이 커진다. 회사명·수치·기여도·성과를 생성 모델이 메워서는 안 된다.

**개선:** 출력 전에 “근거 있음/사용자 확인/추정 금지/정보 부족” 상태를 분리한다. 부족한 값은 문장을 생성하지 말고 질문한다.

### B. 실행 인프라 파이프라인

#### 긴 작업이 하나의 웹 서버에 몰림 — 확인

Express 프로세스 하나가 일반 API, AI 호출, 파일 파싱, 메모리 업로드, Puppeteer PDF, PPT 생성을 함께 처리한다. 요청 제한 시간은 최대 5분이고 업로드는 25MB까지 메모리에 보관한다. 배포 설정은 Render 무료 인스턴스다.

Render는 무료 웹 서비스가 15분 동안 요청이 없으면 대기 상태로 들어가고, 운영용으로 사용하지 말라고 명시한다. 긴 작업은 웹 요청과 분리된 백그라운드 워커 구조가 적절하다. [Render 무료 인스턴스](https://render.com/docs/free), [Render 서비스 유형](https://render.com/docs/service-types)

**위험:** 동시 요청 때 메모리·CPU 경합, 콜드 스타트, 연결 종료, 중복 과금, 새로고침 후 진행 상태 소실.

**목표 구조:** 

```text
브라우저 ── 업로드/작업 요청 ──> Web API
                                  │
                                  ├─ job_id 즉시 반환
                                  ↓
                               작업 큐
                                  ↓
             AI worker / parser worker / export worker
                                  ↓
                       Firestore 상태 + Storage 결과
                                  ↓
                     폴링 또는 실시간 진행 알림
```

작업에는 최소한 `job_id`, `idempotency_key`, `queued/running/succeeded/failed`, 진행률, 재시도 횟수, 모델·프롬프트 버전, 비용, 오류 코드를 저장한다.

#### 속도 제한이 사용자 기준처럼 보이지만 IP 기준으로 동작 — 확인

일반 제한기와 일부 AI/내보내기 제한기가 인증 미들웨어보다 먼저 적용돼 `req.user`가 없다. 결과적으로 같은 학교·회사·기숙사 네트워크의 사용자가 하나의 IP 한도를 공유할 수 있다.

**개선:** 인증 이후 사용자 한도와 인증 이전 IP 한도를 분리한다. 비AI 내보내기와 AI 생성 제한기도 구분한다.

#### 모델 폴백이 품질을 바꿔도 드러나지 않음 — 확인

Pro/Flash/Lite 폴백은 가용성을 높이지만, 같은 요청이 서로 다른 품질의 결과를 낼 수 있다. 사용자는 어떤 모델·프롬프트·폴백이 쓰였는지 모르고, 운영자도 결과 품질을 버전별로 비교하기 어렵다.

**개선:** 결과 문서에 내부 모델·프롬프트 버전을 기록하고, 골든셋 품질 기준을 통과한 폴백만 허용한다. 사용자에게는 장애로 저품질 결과를 조용히 제공하기보다 재시도 가능 상태를 알려야 한다.

### C. 가져오기·파일 파이프라인

#### 임의 URL 접근 위험 — 확인

블로그 가져오기는 사용자가 입력한 URL을 서버가 리디렉션을 따라 요청하고 브라우저 자동화로 열 수 있다. 코드상 사설 IP, localhost, 클라우드 메타데이터 주소를 차단하는 검사가 확인되지 않았다.

**개선:** DNS 해석 전후 사설·루프백·링크로컬 차단, 허용 프로토콜을 HTTPS/HTTP로 제한, 리디렉션마다 재검사, 응답 크기·시간 제한, 가능하면 도메인 허용 목록을 적용한다.

#### 파일 검증과 삭제 권한 — 확인

- 업로드는 MIME/확장자 중심이며 ZIP의 압축 해제 크기 제한이 명확하지 않다.
- 이미지 삭제 API는 로그인은 확인하지만 요청한 Storage 경로가 해당 사용자 소유인지 검증하지 않는다.

**개선:** 압축폭탄·파일 시그니처 검사, 저장 경로를 서버가 생성, 삭제 시 `users/{uid}/...` 소유권 확인, 다운로드는 짧은 만료의 서명 URL을 사용한다.

### D. 결제·크레딧 파이프라인

#### 결제의 진실이 두 컬렉션에 나뉨 — 확인

- 자동 결제용 `creditOrders`: 9건, 현재 모두 pending, paid 0건
- 수동 계좌이체용 `creditRequests`: 3건, 승인 2건, 거절 1건

승인 두 건의 표시 금액 합계는 6,000원 수준이지만 실제 입금·환불은 은행 대사 없이 확정 매출로 볼 수 없다. 현재 화면은 PortOne 코드를 불러오면서도 실제 구매 경로는 수동 입금 요청이다. 응답 데이터에는 `crwedits` 오타도 있다.

**개선:** 하나의 Payment 엔터티와 불변 원장을 사용한다.

```text
created → awaiting_payment → paid → credits_granted
                               └→ refunded / chargeback
```

- 제공자 거래 ID와 idempotency key를 유일값으로 관리
- 승인과 크레딧 지급을 하나의 트랜잭션으로 처리
- 금액, 세금, 환불, 지급 크레딧, 운영자, 근거를 감사 로그로 저장
- 수동 결제를 유지한다면 화면에 “베타 수동 승인, 예상 처리 시간”을 명시
- 광고 집행 전에 결제 성공·중복 방지·환불을 실제 소액으로 종단 테스트

### E. 계정·개인정보 파이프라인

#### “모든 데이터 삭제”와 실제 삭제 범위가 다름 — 확인

계정 삭제는 경험, 포트폴리오, 채용 매칭과 Auth 계정을 지우지만 프로필, 가져오기, 크레딧 지갑·하위 거래, 주문·요청, 피드백, 오류 로그, Storage 업로드는 삭제하지 않는다. 사용자에게는 모든 데이터가 삭제된다고 안내한다.

**개선:** 데이터 맵을 만들고 즉시 삭제, 법적 보존, 익명화 대상을 구분한다. 삭제 작업도 큐로 만들고 항목별 완료를 검증한 뒤 사용자에게 영수증을 제공한다.

개인정보 처리방침에는 보유기간, 수탁자·국외 이전, 파기 방법, AI 제공자 처리, 권리 행사 절차, 연락처가 구체적으로 필요하다. 개인정보보호위원회는 처리방침 작성지침과 생성형 AI 개발·활용 안내서를 제공한다. [개인정보 처리방침 작성지침](https://m.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=11133), [생성형 AI 개인정보 안내서](https://m.pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS212&mCode=C040030000&nttId=11360)

#### 관리자 인증이 운영 규모를 견디기 어려움 — 확인

관리자 화면은 별도 아이디·비밀번호를 브라우저 세션에 저장하고 각 요청 본문에 보낸다. 서버 세션, MFA, 역할, 작업별 감사 로그가 없다.

**개선:** Firebase custom claims 또는 별도 IdP 기반 서버 검증, MFA, 최소 권한 역할, 관리자 작업 감사 로그, 비밀값 회전, 로그인 실패 제한을 적용한다.

## 7. 성능·품질·유지보수 진단

### 빌드와 번들

현재 프론트엔드 프로덕션 빌드는 통과한다. 다만 코드 편집기 관련 단일 청크가 약 11.2MB(minified), gzip 약 2.15MB이며 다른 편집·페이지 청크도 크다. 모든 사용자에게 개발자용 코드 편집기 기능을 일찍 내려보내면 첫 경험을 악화시킬 수 있다.

**개선:** 직무별·편집기별 동적 import, 개발자 직무에서만 코드 플러그인 로딩, 아이콘·에디터 플러그인 사용량 점검, 실제 모바일 네트워크에서 재측정한다.

과거 내부 Lighthouse 문서의 홈 성능 점수는 65였고 큰 로고 문제는 이후 수정되었다고 기록돼 있다. 현재 PageSpeed API 재측정은 할당량 제한으로 완료하지 못했으므로 과거 점수를 현재값으로 사용하면 안 된다.

### 오류

최근 30일 오류 123건, 영향을 받은 사용자는 10명이다. 빈도는 브라우저 전역 오류, API 500/502, 경험 생성, 이력서·포트폴리오 PDF에 집중된다. 사용자 규모가 작기 때문에 오류 사용자 10명은 무시할 수 없다.

**개선 우선순위:**

1. 내보내기 성공 여부와 실패 코드를 서버 사건으로 기록
2. 동일 작업 중복 요청 방지와 안전한 재시도
3. 익명 오류의 사용자·작업 상관관계 연결
4. 오류 메시지에 복구 행동 제공
5. 매주 상위 3개 오류를 재현 테스트로 고정

### 테스트와 코드 구조

- JS/JSX 약 10.5만 줄, 1,000줄을 넘는 파일 23개
- 가장 큰 템플릿·편집기·결과 페이지는 5,000~9,000줄 규모
- 일반적인 단위/통합/E2E 테스트와 CI 구성이 확인되지 않음
- 프로덕션 의존성 감사에서 프론트엔드 21건, 백엔드 25건의 알려진 취약점이 보고됨. critical/high에는 PDF, 메일, WebSocket 등 직접·간접 의존성이 포함됨

`npm audit`은 실제 공격 가능성을 자동 판정하지 않으므로 즉시 전부 강제 업데이트하기보다 도달 가능성, 외부 입력, 수정 버전, 회귀 위험을 분류해야 한다. 단, URL 가져오기·파일 파싱·관리자·PDF처럼 외부 입력과 권한이 만나는 경로의 critical/high는 P0다.

## 8. 비용 구조와 수익화 한계

### 확인된 AI 사용

- 사용성 거래 770건
- 기록된 AI 비용 약 $42.98, 내부 환산 약 58,000원
- 지갑 총사용 크레딧 약 487,000, 거래 컬렉션의 사용 크레딧 약 206,000으로 불일치
- 비용 상위는 경험 추출, 채용공고 분석, GitHub 경험 추출
- 일부 레거시 요청과 검색 그라운딩 비용은 원가에 완전히 반영되지 않음

Gemini 공식 가격은 모델·토큰·검색 그라운딩에 따라 달라지며, 현재 코드의 주요 토큰 단가는 공식 가격과 대체로 일치한다. 그러나 검색 도구 비용과 실패·재시도·레거시 모델까지 잡지 않으면 기능별 마진을 잘못 계산한다. [Gemini API 가격](https://ai.google.dev/gemini-api/docs/pricing)

Firebase는 무료 할당량이 있지만 예산 알림이 과금을 자동으로 차단하지는 않는다. 비용 상한은 제품 레벨에서 별도로 두어야 한다. [Firebase 요금제](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans)

### 현재 수익화의 구조적 문제

1. 취업 준비는 매일 쓰는 범용 SaaS보다 특정 기간에 몰리는 사건형 수요다.
2. 사용자는 “크레딧”보다 “한 회사 지원 패키지”의 가치를 이해하기 쉽다.
3. 수동 계좌이체는 가장 지불 의사가 높은 순간에 기다림과 불신을 만든다.
4. 결과물의 신뢰와 내보내기 안정성이 확인되기 전에 결제 최적화를 해도 전환되지 않는다.

### 권장 가격 구조

- 내부 원가 관리는 크레딧으로 유지
- 사용자에게는 결과 단위로 표시: 예) 경험 분석 1회, 회사 맞춤 지원 패키지 1개, PDF/PPT 내보내기 포함
- 초기는 일회성 패키지를 기본으로 하고, 여러 회사에 적극 지원하는 사용자가 확인되면 기간제 플랜 실험
- 대학·부트캠프·커리어 코치에는 좌석보다 “활성 코호트 + 관리자 검토 + 결과 리포트” 라이선스 검토

구독은 반복 루프가 검증된 뒤에 해야 한다. 완성 후 떠나는 사용자를 구독으로 묶으려 하면 환불·불만만 늘어난다.

### 직접·인접 대체재

| 디자인/웹 포트폴리오 | Canva, Notion Sites | 쉬운 편집, 익숙한 브랜드, 풍부한 템플릿, 공유 | 디자인 경쟁을 피하고 검증된 콘텐츠를 이 도구들로 내보내는 허브가 됨 |

Teal은 채용공고 추적과 맞춤 이력서를, Huntr는 저장한 공고에 맞춤 이력서를 묶는 application packet을 중심에 둔다. [Teal](https://www.tealhq.com/how-it-works), [Huntr Application Packets](https://help.huntr.co/en/articles/14367332-application-hub-and-packets)

Kickresume은 AI 이력서, ATS 점검, 커버레터, 웹사이트까지 폭넓게 제공한다. [Kickresume](https://www.kickresume.com/en/ai-resume-writer/)

Notion과 Canva는 이미 포트폴리오 웹 공개·템플릿·PDF/공유 경험이 강하다. [Notion Sites](https://www.notion.com/en-gb/help/public-pages-and-web-publishing), [Canva 포트폴리오](https://www.canva.com/create/portfolios/)

국내에서는 채용 달력·공고·자기소개서·커뮤니티가 묶인 자소설닷컴 같은 서비스가 사용자의 취업 준비 시간을 점유한다. [자소설닷컴](https://jasoseol.com/)

### 피해야 할 경쟁

- “템플릿이 더 많다”
- “AI가 더 예쁘게 써 준다”
- “모든 직무를 지원한다”
- “한 제품에 모든 취업 기능이 있다”

이 영역은 거대 디자인 도구와 해외 이력서 플랫폼이 규모·브랜드·템플릿 수에서 유리하다.

### 가져가야 할 포지션

> “파일과 프로젝트 기록을 넣으면, 핏폴리가 사실 근거를 찾아 확인받고, 지원 회사마다 바로 쓸 수 있는 경험 패키지로 바꿔 준다.”

핵심 차별 요소는 다음 넷이어야 한다.

1. 다양한 한국형 자료에서 경험을 추출하는 능력
2. 원문 근거와 사용자 확인이 붙은 사실성
3. 회사·공고가 바뀌어도 재사용되는 경험 그래프
4. 실제 지원과 결과까지 이어지는 반복 루프

### 초기 고객군

현재 직무 데이터가 비어 있으므로 “개발자가 가장 좋다” 같은 결론은 낼 수 없다. 직무보다 다음 조건으로 첫 세그먼트를 잡는 편이 낫다.

- 30일 안에 실제 지원 예정
- 프로젝트·인턴·동아리 자료가 3개 이상 흩어져 있음
- 무엇을 했는지는 있지만 성과 문장으로 정리하지 못함
- 첫 취업 또는 직무 전환으로 증거 선별에 어려움이 큼

한국경제인협회 조사에서는 2025년 대학 졸업예정자·졸업자의 60.5%가 구직 기대가 낮아 사실상 소극적 구직 상태라고 답했다. 시장의 고통은 크지만 이것만으로 결제 의사가 증명되지는 않는다. [한국경제인협회 2025 대학생 취업인식도](https://www.fki.or.kr/kor/news/statement_detail.do?bbs_id=00036790&category=ST)

대학일자리플러스센터는 대학 내 진로·취업 원스톱 서비스를 제공하므로, 검증 이후 B2B2C 파일럿 채널이 될 수 있다. [대학일자리플러스센터](https://certi.keis.or.kr/uei/ueiJobPlusCetr.do)

## 10. 새로 정의할 북극성 지표와 퍼널

### 북극성 지표

**주간 지원준비 완료 사용자(WAPU)**

한 주 안에 다음 조건을 모두 충족한 고유 사용자 수:

1. 원문 근거가 연결된 경험을 하나 이상 확인했고
2. 특정 공고 또는 지원 목표와 연결했으며
3. 내보내기 성공 또는 공유 링크 생성까지 완료

단순 문서 생성이나 AI 호출은 포함하지 않는다.

### 활성화 정의

가입 72시간 안에:

- `extraction_completed`
- `evidence_confirmed` 1개 이상
- `export_succeeded` 또는 `share_created` 1회

세 가지를 모두 만족한 사용자. 72시간을 제안하는 이유는 현재 가치 행동의 대부분이 첫 24시간에 발생하고 72시간 이후 신규 완주가 드물기 때문이다.

### 순서가 있는 퍼널

```text
landing_view
→ signup_started
→ signup_completed
→ first_source_added
→ extraction_completed
→ evidence_confirmed
→ portfolio_generated
→ export_succeeded / share_created
→ second_job_tailored
→ checkout_started
→ purchase_completed
```

Amplitude 역시 퍼널은 정해진 단계와 전환 기간으로, 리텐션은 시작 사건과 복귀 사건으로 정의한다. 도구 선택과 무관하게 이 원칙을 지켜야 한다. [Amplitude 퍼널 정의](https://amplitude.com/docs/analytics/charts/funnel-analysis/funnel-analysis-interpret), [Amplitude 리텐션 정의](https://amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-build)

### 리텐션 사건

로그인이나 페이지뷰가 아니라 다음 중 하나를 복귀로 본다.

- 새 자료 가져오기
- 새 공고에 기존 경험 연결
- 새 지원 결과물 내보내기
- 지원 상태·결과 업데이트

가입 주차별 D1/D7/D30과 첫 활성화 주차별 W1/W4를 따로 본다.

### 반드시 추가할 공통 사건 필드

```text
event_id, event_name, occurred_at
user_id, anonymous_id, session_id
source, utm_*, device
career_stage, job_category, application_deadline_bucket
artifact_id, experience_id, job_id, portfolio_id, template_id
model, prompt_version, fallback_used
latency_ms, success, error_code
credits, estimated_cost_usd
schema_version
```

분석 이벤트에는 이력서 원문, 개인정보, 생성 전문을 넣지 않는다. 식별자는 최소화하고 운영 DB와 분석 DB의 접근 권한·보존기간을 분리한다.

### 대시보드 한 장에 필요한 지표

| 영역 | 지표 |
|---|---|
| 획득 | 방문→가입 완료율, 채널별 활성화율 |
| 첫 가치 | source→extraction 성공률, 중앙값/p95 시간, evidence 확인률 |
| 결과 | portfolio→export 성공률, 빈 문서율, 결과물당 사용자 수정률 |
| 반복 | 30일 내 두 번째 공고 연결률, W1/W4 가치 리텐션 |
| 수익 | checkout→paid, paid→credit granted, 환불, ARPPU |
| 원가 | 활성 사용자당 AI 원가, 성공 내보내기당 원가, 기능별 실패 비용 |
| 신뢰 | 근거 없는 주장률, 사용자 삭제/수정률, 개인정보 요청 처리시간 |
| 안정성 | API p95, AI 작업 p95, export 성공률, crash-free session |

## 11. 운영 체계

### 일일 운영

- 결제 요청·입금·크레딧 지급 대사
- 실패한 AI/내보내기 작업과 재시도 큐
- 오류 급증, 비용 급증, 비정상 URL·파일 요청
- 사용자 문의와 삭제 요청
- 전날 퍼널 데이터 누락 검증

### 주간 운영 리듬

| 요일 | 활동 | 산출물 |
|---|---|---|
| 월 | KPI와 데이터 품질 검토 | 한 장 대시보드, 이상 원인 |
| 화 | 이탈 3명 + 완주 2명 인터뷰 | 문제 문장, 영상/메모, 빈도 |
| 수 | 신뢰성 집중 수정 | 상위 오류 3개와 회귀 테스트 |
| 목 | 실험 1개 실행·검토 | 가설, 대상, 결과, 결정 |
| 금 | AI 품질·원가·개인정보·릴리스 점검 | 모델 카드, 비용표, 변경 기록 |

팀이 작아 한 사람이 여러 역할을 맡더라도 책임자는 명시한다.

- 제품·퍼널 책임자
- AI 품질·프롬프트 책임자
- 플랫폼·내보내기 신뢰성 책임자
- 결제·지원·개인정보 책임자

### 장애 등급

| 등급 | 예시 | 대응 |
|---|---|---|
| Sev0 | 개인정보 노출, 타인 파일 삭제, 중복 결제/크레딧 | 즉시 기능 중지, 비밀 회전, 영향 범위 보존·통지 검토 |
| Sev1 | 가입·결제·내보내기 전체 장애 | 1시간 안에 확인, 우회/롤백, 상태 공지 |
| Sev2 | 특정 파일·모델·브라우저의 반복 실패 | 당일 분류·대응 |
| Sev3 | 문구·레이아웃·경미한 편집 문제 | 일반 백로그 |

### 초기 서비스 목표(SLO)

- 비AI API p95 < 500ms
- AI 작업 접수 응답 < 2초
- 경험 추출 p95 < 120초
- PDF/PPT 내보내기 성공률 ≥ 99%
- 결제 후 크레딧 지급 성공률 100%, 중복 지급 0
- 오류 없는 세션 ≥ 99.5%
- 영업일 문의 최초 응답 < 1일

이는 시장 평균 주장이 아니라 초기 운영 목표다. 실제 분포를 수집한 뒤 비용과 사용자 기대에 맞춰 조정한다.

### AI 품질 운영

직무 4개 × 입력 품질 3단계 × 자료 형식 4개의 골든셋을 만든다. 각 버전에서 다음을 자동·수동 평가한다.

- 근거 없는 사실·수치 생성률
- 원문 핵심 사실 회수율
- 역할과 팀 성과의 분리
- 사용자가 삭제·대폭 수정한 문장 비율
- 공고 요구역량과 근거 경험의 연결 적합성
- 모델별 지연과 원가

모델이나 프롬프트를 바꿀 때 골든셋을 통과하지 못하면 배포하지 않는다.

## 12. 12주 우선순위 로드맵

### P0 — 0~2주: 측정과 신뢰 경로 복구

1. 신규 템플릿·직무·출력 형식 추가를 일시 중지
2. 사건 스키마와 순서형 퍼널 구현
3. 대시보드의 사용자 ID, 퍼널, 활성화, TTV 계산 수정
4. `creditOrders`와 `creditRequests`를 하나의 결제 원장으로 통합하고 승인 2건 대사
5. PDF/PPT/경험 생성의 성공·실패·재시도 계측
6. 계정 삭제 범위, Storage 삭제 권한, URL SSRF, 관리자 인증 수정
7. critical/high 의존성 도달 가능성 분류와 우선 패치
8. 개인정보 처리방침과 실제 데이터 생명주기 일치

**통과 조건:** 모든 신규 가입자가 어느 단계에서 멈췄는지 알 수 있고, 결제·내보내기·삭제에 종단 테스트가 존재한다.

### P1 — 3~6주: 첫 가치 단순화

1. 프로필 우선 대신 `목표 + 마감일 + 자료 1개`로 시작
2. 자료 업로드 뒤 원문 근거가 붙은 경험 확인 화면 제공
3. 템플릿은 추천 1개만 먼저 보여 주고 나머지는 고급 설정으로 이동
4. AI·파싱·내보내기를 작업 큐와 워커로 분리
5. 모델·프롬프트 버전과 골든셋 회귀 평가 구축
6. 실행 전에 예상 크레딧·시간 표시, 실패 시 자동 환불
7. 모바일 저속 환경과 Google 인앱 브라우저 종단 테스트

**통과 조건:** 가입 72시간 활성화율과 source→export 성공률이 기준선보다 명확히 개선되고, 내보내기 성공률 99%에 근접한다.

### P2 — 7~12주: 반복 사용과 채널 검증

1. 결과물 생성 후 공고 저장·지원 상태·다음 행동 제공
2. 기존 경험을 두 번째 공고에 재사용하는 기본 흐름 구축
3. 지원 결과를 사용자가 선택적으로 입력하고 가치 피드백 제공
4. 측정된 상위 1~2개 세그먼트에만 직무별 출력 고도화
5. 대학·부트캠프·커리어 코치 한 곳과 소규모 코호트 파일럿
6. 결과 단위 가격과 기간제 플랜을 실제 결제로 실험

**통과 조건:** 30일 안에 두 번째 공고를 연결하는 사용자가 생기고, 한 코호트에서 반복 사용·운영비·결제 의사를 함께 확인한다.

### 당분간 하지 않을 것

- 더 많은 템플릿과 직무 프롬프트
- 퍼널·결제가 고쳐지기 전 유료 광고
- 응답자 14명의 평점으로 PMF 선언
- 로그인 시각을 리텐션으로 보고하는 일
- 근거 없는 랜딩 통계와 “12분” 약속 확대
- 불안정한 자동화를 숨기고 성공처럼 표시하는 것

## 13. 우선 실행할 실험 6개

| 실험 | 대조 | 핵심 지표 | 안전 지표 |
|---|---|---|---|
| Artifact-first 온보딩 | 프로필 먼저 vs 자료 1개 먼저 | 72시간 활성화 | 업로드 실패, 삭제 요청 |
| 선택 축소 | 템플릿 전체 vs 추천 1개+고급 | portfolio→export | 선택 변경, 지원 문의 |
| 근거 표시 | AI 문장만 vs 원문 근거+확인 | evidence_confirmed, 대폭 수정률 | 처리시간, 비용 |
| 비동기 작업 | 화면 대기 vs 작업 큐+복귀 | 추출/내보내기 완료율 | 중복 실행, 환불 |
| 결과 단위 가격 | 크레딧 표시 vs 지원 패키지 | checkout→paid | 환불, 지원 문의 |
| 두 번째 공고 루프 | 완료 화면 vs 다음 공고 연결 | 30일 내 second_job_tailored | 알림 해제, 피로도 |

사용자 수가 작으므로 통계적 유의성만 기다리면 지나치게 오래 걸린다. 각 실험은 전환 방향, 실패 로그, 인터뷰를 함께 보고 결정한다. 표본이 매우 작을 때는 숫자를 퍼센트만으로 과장하지 말고 분자/분모를 함께 표시한다.

## 14. 즉시 확인해야 할 질문

다음 질문에 데이터로 답할 수 있을 때 제품을 체계적으로 운영한다고 말할 수 있다.

1. 지난주 신규 가입자 중 몇 명이 자료를 넣고, 근거를 확인하고, 실제 파일을 받았나?

## 15. 최종 제안

핏폴리에는 이미 중요한 원석이 있다. 96명의 사용자가 741개의 자료를 가져왔다는 사실은 단순 템플릿보다 “흩어진 경력 자료를 정리하고 싶다”는 행동이 존재함을 보여 준다. 하지만 지금은 그 자료가 검증된 경험, 지원 회사별 결과물, 실제 지원, 재사용, 결제로 이어지는 과정이 느슨하고 측정되지 않는다.

따라서 제품의 중심을 다음처럼 바꿔야 한다.

```text
많은 AI 기능과 템플릿
        ↓
한 자료에서 사실 근거를 뽑고
사용자가 확인한 뒤
한 회사 지원에 실제로 쓰고
다음 회사에서 다시 쓰는 루프
```

핏폴리의 방어력은 생성 문장의 화려함이 아니라 **증거의 출처, 사용자 확인, 지원처별 재사용 이력, 결과 피드백**에서 생긴다. 운영 역시 기능 출시 개수가 아니라 “이번 주 몇 명이 검증된 경험으로 지원 준비를 끝냈는가”를 중심으로 돌아가야 한다.

## 부록 B. 데이터 해석 주의

- 현재 집계는 컬렉션 생성 데이터이며 완주 행동을 직접 의미하지 않는다.
- Firebase `lastSignInTime`은 제품 리텐션이 아니다.
- 승인된 수동 결제 요청은 은행 대사 전까지 확정 매출로 단정하지 않는다.
- 기록된 AI 원가는 레거시·검색·실패 재시도를 완전히 포함하지 않을 수 있다.
- 외부 시장 통계는 원문 출처와 조사 표본을 랜딩·IR 자료에 함께 표시해야 한다.
- 이 문서의 보안 발견은 코드 정적 점검이며 별도 침투 테스트를 수행한 결과가 아니다.
